# Сквозная надёжность всех сохранений без VPN

**Дата:** 2026-08-10
**Статус:** approved for implementation
**Область:** все формы `calc.recycleobject.ru` и `calc2.recycleobject.ru`, Yandex platform API

## Контекст

Версия v440 сделала сохранение калькулятора атомарным, однако приложение содержит
75 функций записи данных и более 100 вызовов `insert`/`upsert`/`update`/`delete`.
Обычные формы используют общий `POST /api/compat/query`, а вложения — storage API.
До этого только атомарный снимок заказа автоматически повторял краткий сетевой
сбой. Остальные формы могли получить timeout и показать общую красную плашку,
хотя сервер уже завершил запись.

## Цель

Все пользовательские сохранения должны иметь один проверяемый контракт:

- краткий сетевой обрыв или `502/503/504` безопасно повторяется один раз;
- повтор использует тот же `Idempotency-Key`;
- параллельные запросы с одним ключом выполняют мутацию только один раз;
- `insert`, `upsert`, `update` и `delete` не создают дублей при потерянном ответе;
- загрузка и удаление файлов повторяются безопасно с тем же ключом;
- временный сбой, восстановившийся на повторе, не включает красную плашку;
- исчерпанный повтор показывает проблему связи, а следующий успешный запрос
  автоматически снимает плашку;
- атомарный калькулятор, очередь manual/autosave и защита статуса заказа не
  регрессируют.

## Решение

1. Сериализовать обработку одинакового `Idempotency-Key` в API advisory lock до
   проверки кэша и держать блокировку до фиксации сохранённого ответа.
2. Направить все мутации query-builder через общий retry transport с timeout на
   попытку и стабильным ключом.
3. Использовать тот же retry transport для upload/remove storage операций.
4. На уровне data layer различать успешное восстановление и исчерпанный
   connectivity error, чтобы баннер не появлялся после успешного retry и не
   скрывал настоящий постоянный сбой.
5. Добавить матрицу отказов и полный regression gate в deploy workflow.

## Матрица проверки

| Контур | Сценарии |
| --- | --- |
| Атомарный заказ | network error, `502/503/504`, replay, rollback, empty-items safety |
| Общие таблицы | `insert`, `upsert`, `update`, `delete`, lost response, concurrent replay |
| Файлы | upload/remove, network retry, стабильный idempotency key |
| UI/data layer | transient recovery без плашки, persistent failure с плашкой, auto-clear |
| Calculator | manual/autosave ordering, local backup, status preservation |
| Production | API health, live-site, mirror и write-back smoke на обоих доменах |

## Инварианты и границы

- Публичные API `Calculator`, `Warehouse` и схема `items` не меняются.
- Схема бизнес-таблиц не меняется; новая миграция не требуется.
- Ошибки валидации и `4xx` не повторяются.
- Select/read запросы не превращаются в мутации и не получают mutation retry.
- Реальные production-данные не создаются для ручной проверки без отдельной
  необходимости; write-back smoke использует маркированные строки и cleanup.

## Приёмка

- Новые fault-injection тесты проходят локально и в CI.
- Весь существующий smoke-набор остаётся зелёным.
- Версия и cache-bust изменённых скриптов синхронны.
- После deploy оба домена показывают одну версию, API/DB health зелёный, live,
  mirror и write-back workflows завершены успешно.
