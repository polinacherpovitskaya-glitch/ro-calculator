# Timebot: независимый мониторинг и аварийные уведомления

## Проблема

Учёт производственных часов зависит от Telegram-бота. Запущенный Docker-контейнер
сам по себе не доказывает, что бот продолжает опрашивать Telegram, видит Yandex DB
и способен принимать отчёты. О сбое сейчас можно узнать только от сотрудников.

## Требуемое поведение

- Бот раз в минуту записывает в постоянный volume health-снимок.
- Health-снимок подтверждает:
  - процесс и event loop работают;
  - Telegram API доступен через рабочий relay;
  - Yandex DB отвечает;
  - long polling остаётся включённым.
- Независимый GitHub Actions monitor запускается каждые 5 минут и сразу после
  деплоя Timebot.
- Monitor отдельно проверяет:
  - доступность Yandex VM по SSH;
  - состояние контейнера `ro-timebot`;
  - свежесть и результат health-снимка;
  - Telegram relay снаружи VM;
  - чтение из Yandex Supabase снаружи VM.
- При первом падении Полина получает Telegram-уведомление со ссылкой на run,
  а GitHub создаёт incident issue.
- Повторные проверки одного и того же падения не присылают одинаковые сообщения.
- После восстановления приходит отдельное Telegram-уведомление, incident issue
  закрывается автоматически.
- Успешные регулярные проверки не отправляют сообщения.

## Допустимая задержка

Штатная проверка идёт каждые 5 минут. С учётом очереди GitHub Actions целевая
задержка обнаружения — 5–10 минут.

## Безопасность

- Токены Telegram, SSH-ключ и chat ID остаются только в GitHub Secrets.
- Health-файл не содержит токенов, URL с секретами или персональных данных.
- Проверка Yandex DB выполняет только чтение одной строки.

## Границы

- Monitor не создаёт тестовые записи часов.
- Telegram relay пока остаётся транспортным исключением; monitor отдельно
  контролирует его доступность.
- Если GitHub Actions недоступен глобально, внешний alert может задержаться;
  локальный health-файл продолжит обновляться для диагностики.

## Приёмка

- Свежий healthy snapshot проходит проверку.
- Старый, повреждённый или unhealthy snapshot завершает workflow ошибкой.
- Остановленный/перезапускающийся контейнер завершает workflow ошибкой.
- Недоступный relay или Yandex DB завершает workflow ошибкой.
- Первый сбой создаёт один alert, повторный сбой не спамит, восстановление
  отправляет один recovery alert.
- Версия приложения повышена до `v420`.
