# Производственный календарь: непрерывные полосы заказов

Дата: 2026-07-30

## Контекст

Версия `v430` перевела календарь с одной строки на заказ на четыре честные
линии людей. Ресурсный расчёт теперь не создаёт пятого сотрудника и сохраняет
внутрисменное время, но визуальная модель всё ещё дробит работу на отдельные
карточки каждого дня.

На длинном заказе это создаёт несколько проблем:

- один заказ на двух людях выглядит как набор независимых работ;
- название и этап повторяются в каждой дневной ячейке и почти всегда обрезаны;
- переходы между заказами, этапами и рабочими днями выглядят одинаково;
- связь выбранного числа людей с фактическими линиями видна только при
  наведении;
- цвет обозначает только этап, поэтому два соседних заказа одного этапа
  визуально сливаются;
- дедлайн связан с заказом только маленьким номером в отдельной строке.

## Цель

Сделать диаграмму читаемой как план проектов:

- один заказ легко проследить от старта до готовности;
- выбранные 2–4 человека сразу читаются как одна команда заказа;
- этапы остаются различимыми, но не разбивают заказ на дневные «баблы»;
- порядок слева остаётся строгим правилом распределения свободных людей;
- начало, завершение и дедлайн заказа видны без наведения.

## Инвариант планирования

Очередь читается сверху вниз и не может быть обойдена заказом ниже:

1. первый готовый заказ получает до сохранённого числа людей;
2. следующий заказ получает первый оставшийся свободный слот;
3. затем распределяется следующий заказ;
4. после освобождения слота он снова выдаётся первому незавершённому заказу,
   которому ещё можно добавить человека;
5. при `4 чел.` верхний заказ занимает все четыре линии, и нижние заказы
   стартуют только после освобождения человека.

Пример для четырёх людей:

- Т‑банк, `2 чел.` → линии 1 и 2;
- e‑code, `1 чел.` → линия 3;
- следующий заказ, `1 чел.` → линия 4.

Это уже близко к текущему расчёту, но становится отдельным проверяемым
контрактом, а не побочным результатом обхода массива.

## Непрерывная полоса заказа

### Оболочка

На каждой линии последовательные интервалы одного заказа объединяются в один
`order run`.

- оболочка начинается в фактический час первого интервала;
- оболочка заканчивается в фактический час последнего интервала;
- соседние рабочие дни одного запуска не создают новые скруглённые карточки;
- выходные и праздники внутри длинного запуска остаются незалитыми и
  показываются тонким пунктирным соединением, чтобы не изображать работу в
  нерабочее время;
- новый `order run` начинается только после реального переключения этой линии
  на другой заказ.

### Содержимое

Внутри оболочки:

- один раз показаны номер приоритета и короткое название заказа;
- справа показана прогнозная дата готовности;
- этапы обозначены тонкими цветными секциями:
  - оранжевый — литьё;
  - бирюзовый — сборка;
  - фиолетовый — упаковка;
- граница этапа не получает отдельного скругления и не выглядит новым
  проектом;
- узкие секции сохраняют подсказку с полным названием, датой и временем.

У каждого заказа есть стабильный цвет проекта из контрастной палитры. Он
используется для внешнего контура, номера приоритета и связей между линиями;
цвет этапа остаётся внутри полосы.

## Несколько людей на одном заказе

Если в один момент заказ выполняют несколько людей:

- их полосы имеют один проектный цвет, одинаковый номер и название;
- в точке начала рисуется вертикальная скоба между занятыми линиями;
- рядом со скобой показано `2 чел.`, `3 чел.` или `4 чел.`;
- внутри каждой полосы есть компактный индекс `1/2`, `2/2` и так далее;
- наведение на любую полосу сохраняет остальные заказы читаемыми: они
  приглушаются умеренно, а не исчезают почти полностью.

Скоба строится только для реально одновременных назначений. Она не обещает,
что выбранный максимум людей занят на всём протяжении заказа.

## Начало, завершение и дедлайн

- начало заказа отмечается на первой полосе подписью `Старт`;
- завершение отмечается на последнем интервале подписью `Готово`;
- дедлайн остаётся на общей шкале и получает проектный цвет, номер и короткое
  имя при доступной ширине;
- при наведении дедлайн, очередь и все полосы заказа подсвечиваются вместе;
- состояние `успеваем / впритык / опаздываем` остаётся в карточке приоритета.

## Очередь слева

- порядок drag-and-drop и прогнозные даты сохраняются;
- контрол меняет подпись с `до N` на `N чел.`, чтобы восприниматься как
  назначение команды на текущий план;
- после пересчёта фактически используемое число линий видно рядом, если оно
  меньше выбранного максимума;
- карточка и полоса используют один проектный цвет;
- разделитель будущих заказов сохраняется.

## Подсветка

Выбранный заказ получает контрастный контур. Остальные элементы остаются
видимыми с непрозрачностью не ниже 55%, потому что сравнение очереди и
параллельной загрузки является основной задачей экрана.

## Совместимость

- формат `production_plan_state_json` не меняется;
- схема БД и API не меняются;
- `production_parallel_workers` остаётся максимумом людей;
- `workerSlot`, `startHour` и `endHour` остаются вычисляемыми;
- публичные API `Calculator` и `Warehouse` не меняются;
- мобильное вертикальное расположение и регулируемая ширина очереди
  сохраняются.

## Не входит в эту волну

- именное назначение сотрудников;
- ручное перетаскивание отдельных этапов между людьми;
- планирование оборудования и молдов;
- изменение производственных нормативов;
- изменение порядка этапов в заказе.

## Acceptance criteria

- два человека верхнего заказа видны на двух соседних линиях как один связанный
  проект;
- три и четыре человека аналогично образуют связанную группу;
- при верхнем заказе на двух людях второй заказ стартует на линии 3, третий —
  на линии 4;
- при верхнем заказе на четырёх людях ни один нижний заказ не стартует
  одновременно;
- непрерывное литьё одного заказа на одной линии в течение нескольких рабочих
  дней имеет одну внешнюю оболочку и одно название;
- внутри оболочки переход этапа не создаёт новый скруглённый бабл;
- выходной внутри длинного запуска не закрашен как рабочее время;
- на диаграмме без наведения видны название проекта, его этапы, прогнозное
  завершение и связанный дедлайн;
- при фокусе остальные заказы остаются читаемыми;
- четыре линии никогда не содержат пересекающиеся работы;
- week/month zoom, ресайз очереди, drag-and-drop, праздники и переход в заказ
  продолжают работать.

## Rollback

Изменение ограничено клиентской группировкой schedule-сегментов, HTML и CSS.
Откат возвращает дневные task-баблы; сохранённые данные не требуют миграции.
