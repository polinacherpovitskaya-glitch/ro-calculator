# Устранение зависания склада при открытии

**Дата:** 2026-08-27
**Статус:** implementation ready
**Область:** склад, фоновая сверка проектной фурнитуры

## Проблема

При открытии `#warehouse` основная таблица получает складские позиции, после
чего фоновая сверка проектной фурнитуры загружает детали каждого отслеживаемого
заказа отдельным `loadOrder()` через неограниченный `Promise.all`.

В production это создаёт десятки или сотни одновременных запросов к заказам и
их позициям. Запросы массово завершаются по пятитисекундному timeout, вкладка
перестаёт отвечать, а пользователь продолжает видеть состояние
«Загружаем склад» с нулевыми счётчиками.

## Цель

- Склад должен открываться без шквала запросов к деталям заказов.
- Сверка проектных резервов должна использовать лёгкую пакетную выборку позиций.
- Число одновременно выполняемых пакетных запросов должно быть ограничено.
- Существующая логика резервов, готовности и legacy-исправлений не меняется.

## Решение

1. Использовать общий загрузчик деталей проектной фурнитуры и в фоновой
   сверке, и в одноимённой вкладке склада.
2. Загружать позиции заказов пакетами с `summary: true`, без тяжёлого
   `item_data` и вложений.
3. Ограничить размер пакета и число параллельных загрузчиков.
4. Сохранить прежний `loadOrder()` только как совместимый fallback, если
   пакетный API недоступен в окружении.
5. Добавить smoke, который проверяет пакетирование, лёгкий режим и предел
   параллелизма.

## Инварианты

- Публичные сигнатуры `Warehouse.*`, `loadOrder()` и
  `loadOrderItemsByOrderIds()` не меняются.
- Схема `items` и формат складских резервов не меняются.
- Запись остатков и резервов выполняется по прежним правилам.
- Изменение не затрагивает `production-floor/`.

## Проверка

- `node tests/warehouse-migration-smoke.js`
- `node tests/order-flow-smoke.js`
- `node tests/version-smoke.js`

## Вне области

- Изменение API или схемы PostgreSQL.
- Переписывание склада или общей модели заказов.
- Изменение пятитисекундного сетевого timeout.
