# Заказы первыми, устойчивый вход и быстрый первый экран

Дата: 2026-07-28

## Контекст

Сотрудники ежедневно начинают работу со списка заказов. Сейчас интерфейс:

- показывает в ежедневном меню сначала задачи и лиды, хотя рабочий маршрут начинается с заказов;
- перед загрузкой данных текущей страницы ждёт список сотрудников;
- считает мета-информацию для всех заказов, даже когда на первом экране видны только активные;
- при временной ошибке `/api/auth/legacy-me` трактует её как завершение сессии и вызывает серверный logout;
- ограничивает локальный признак входа 30 днями, а серверную сессию — 60 днями.

На production-снимке 2026-07-28 хранится 369 заказов и 1 252 позиции заказов
объёмом около 35 МБ. На стартовом экране `Active` видны 13 заказов и 52 позиции
объёмом около 135 КБ. Чтение самих заказов из PostgreSQL занимает около 1,4 мс,
поэтому перенос или переписывание базы не требуется.

## Цели

1. При входе без hash открывать `#orders`.
2. Показывать ежедневное меню в порядке:
   `Заказы → Калькулятор → Задачи → Лиды`.
3. Не просить повторный пароль на том же компьютере в течение года, пока:
   - пользователь сам не нажал «Выйти»;
   - сервер явно не ответил, что сессия истекла или учётная запись отключена.
4. Не отзывать рабочую серверную сессию из-за временной ошибки сети или ответа 5xx.
5. Начинать загрузку текущей страницы без ожидания удалённого списка сотрудников.
6. На стартовом режиме заказов загружать тяжёлую мета-информацию только для
   действительно видимых заказов.
7. Не запускать параллельно дублирующиеся запросы производственной нагрузки при
   нескольких последовательных render.

## Поведение

### Вход

- Локальный признак входа хранит идентификатор пользователя без собственного
  короткого срока жизни; действительность проверяет защищённая cookie сервера.
- Cookie и запись серверной сессии имеют одинаковый срок 365 дней.
- Успешный `/api/auth/legacy-me` обновляет безопасный локальный снимок профиля.
- При сетевой ошибке, 429 или 5xx приложение временно использует безопасный
  локальный снимок профиля и продолжает работу с локальными fallback-данными.
- Только 401, 403, 404 или несовпадение идентификатора пользователя очищают
  локальный вход. Такой путь не отправляет лишний `/logout`, поскольку сервер уже
  признал сессию недействительной.
- Явная кнопка «Выйти» по-прежнему отзывает серверную сессию и очищает локальные
  данные входа.

### Заказы

- `Orders.loadList()` сначала рисует кэш, затем обновляет заголовки заказов.
- Мета-информация строится по `Orders.getModeOrders()`, а не по всему массиву.
- При переключении на более широкий режим недостающая мета-информация
  догружается и объединяется с уже рассчитанной.
- Корзина мета-информацию не запрашивает.
- Запросы табеля, производственного плана и отпусков для полосы нагрузки
  объединяются в один in-flight Promise и не дублируются между render.

## Совместимость и безопасность

- Схема заказов, Supabase-архив, compatibility store и публичные API модулей не
  меняются.
- Ничего не удаляется.
- Статический выпуск откатывается предыдущим git commit.
- API deploy перед изменением auth автоматически создаёт и проверяет production
  dump; существующая политика нескольких резервных копий сохраняется.
- Изменения не переименовывают DOM id и межмодульные методы из Agent Guide.

## Не входит в этот выпуск

Интеграция с AmoCRM оформляется отдельным подпроектом и PR. Для неё нужны
подтверждённые домен аккаунта, pipeline/status, правило сопоставления менеджеров
CRM с сотрудниками калькулятора и способ приёма событий. До этого placeholder
`Лиды` и поле `crm_link` остаются без изменения.

## Критерии приёмки

- Новый пользователь без hash после входа видит страницу заказов.
- Первые четыре ежедневных пункта меню идут в заданном порядке.
- Перезагрузка с валидной cookie не показывает экран выбора сотрудника.
- Временный сбой `/legacy-me` не вызывает `/logout` и не очищает user id.
- Явный 401 очищает локальную сессию и показывает вход.
- Первый режим `Active` запрашивает мета-информацию только для активных заказов.
- Переход на `Доску` догружает отсутствующие данные.
- Все профильные smoke-тесты и четыре post-deploy workflow проходят.
