# Резервы фурнитуры: обновлять на месте, а не снимать и создавать заново

## Проблема

Резервы склада — одна строка `warehouse_reservations.reservations_data` (JSON-список). На
2026-10-28 в ней 8 282 записи (≈2,19 МБ): 11 `active`, 8 271 `released`, все
`source: 'project_hardware'`. Каждое сохранение заказа и каждое открытие склада читает весь
список (≈2,2 МБ), а после PR #310 — ещё и шлёт патч из десятков записей.

Откуда растёт: оба пути синхронизации резервов фурнитуры/упаковки сначала **снимают все**
активные авто-резервы, а потом **создают новые** записи с новым `id`, даже если ничего не
поменялось:

- `Warehouse.reconcileProjectHardwareReservations()` — на каждое открытие склада (и фоновую
  синхронизацию) снимает авто-резервы **всех** заказов и создаёт их заново. По данным прода это
  92 % мусора: 7 644 из 8 271 снятых записей созданы пачками, где одно `created_at` у нескольких
  заказов. Все 11 текущих активных созданы одной пачкой в 12:46:26.
- `Warehouse.syncProjectHardwareOrderState()` — на каждое сохранение заказа (и смену статуса)
  делает то же для позиций этого заказа. Например, «Обвесы Миллениум»: 222 снятых + 2 активных.

Темп — ≈350 снятых записей в неделю. Попутно: 89 повторяющихся `id` (новые id =
`Date.now() + random(1000)`, пачка из ~11 записей за одну миллисекунду иногда совпадает).

## Решение

### A. Синхронизация применяет разницу
Распределение остатка не меняется: тот же порядок приоритетов, тот же расчёт «доступно =
остаток − чужие активные резервы», та же логика «собрано → не резервируем». Меняется только
применение результата: для каждой пары (заказ, позиция) нужное количество сравнивается с тем,
что уже стоит в активных авто-резервах этой пары:

- совпадает → запись не трогаем;
- отличается → меняем `qty` первой записи на месте (+ `updated_at`/`updated_by`), лишние
  записи пары снимаем;
- нужно 0 → снимаем;
- записи не было → создаём одну новую (с `id`, которого ещё нет в списке).

Название заказа в резерве обновляется на месте, если заказ переименовали.

Итог: повторное сохранение того же заказа и повторное открытие склада **ничего не пишут**
(пустой патч → запроса нет), список не растёт. Резерв живёт одной записью, пока заказ в работе.

### B. Сжатие накопленного (разово, вручную)
`scripts/migrations/2026-10-28-warehouse-reservations-compact.sh` — запускается руками на VM:
1. копия текущего значения строки в `/home/robot/platform-backups/manual/`;
2. в транзакции под тем же advisory-lock, что и `blob-patch` API (`compat:warehouse_reservations`),
   удаляет записи `status = 'released'` с `released_at` старше N дней (по умолчанию 14);
   активные и `cancelled` не трогает;
3. печатает «было/стало» (записей, байт). Без `--apply` — только отчёт (dry run).

Снятые записи в коде никто не читает (только фильтр `status === 'active'`), вкладки с
устаревшей копией не вернут удалённое: патч шлёт только изменённые записи, а `removeIds` —
только то, что вкладка сама удалила.

**Запуск — только после явного «да» Полины.** Ожидаемо (на 2026-10-28): 8 282 → 468 записей
при N = 14 (361 при N = 7, 1 201 при N = 30, 11 — если чистить все снятые).

## Не входит
- Автоматическая чистка старых снятых резервов при каждом сохранении — после сжатия и этого
  фикса рост ≈ единицы записей в день; если понадобится, отдельный PR.
- Чтение всего списка резервов при сохранении заказа (нужен серверный фильтр по заказу) —
  отдельно; после сжатия список маленький.
- Остатки `warehouse_items`, история склада — без изменений.
