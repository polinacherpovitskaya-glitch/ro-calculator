# Автовосстановление сохранения калькулятора

**Дата:** 2026-08-12  
**Статус:** implementation ready  
**Область:** калькулятор заказов, общий Yandex API

## Проблема

Если ручное сохранение заказа завершается сетевой ошибкой, `saveOrder()` безопасно
оставляет полный снимок заказа и позиций в локальном кеше и помечает его как
несинхронизированный. Проверка восстановления связи затем подтверждает доступность
базы и гасит сетевую ошибку, но не отправляет этот локальный снимок автоматически.
Синхронизация запускается только при старте приложения или новом событии `focus`,
поэтому пользователь остаётся на открытой вкладке с фактически несохранённым в
общей базе заказом.

## Цель

- После восстановления общей базы автоматически отправлять локально сохранённые
  `orders` и `orderItems`.
- Не требовать перезагрузки страницы или повторного нажатия «Сохранить».
- Не запускать параллельные recovery-проверки и повторные dirty-sync операции.
- Не скрывать предупреждение, пока заказ всё ещё не синхронизирован.
- После успешной синхронизации сохранить существующий toast и событие обновления
  списка заказов.

## Решение

1. Вынести один проход recovery-проверки в отдельную защищённую от параллельного
   запуска функцию.
2. После успешного probe базы проверить dirty-флаги заказов и вызвать
   `syncDirtyLocalOrders()`.
3. Останавливать recovery-таймер только когда сетевой флаг снят и dirty-заказов
   больше нет.
4. После аварийного локального сохранения повторно запускать recovery-цикл, чтобы
   закрыть гонку между первым probe и установкой dirty-флагов.
5. Добавить регрессионный smoke для сценария «сетевой сбой → локальная копия →
   восстановление → автоматическая запись в общую базу».

## Инварианты

- Публичные сигнатуры `Calculator.saveOrder()` и data-layer функций не меняются.
- Локальная аварийная копия не удаляется до подтверждённой удалённой записи.
- Ошибки доступа и постоянные ошибки валидации не превращаются в бесконечный
  агрессивный retry.
- Синхронизация других локальных наборов данных остаётся вне этой задачи.
