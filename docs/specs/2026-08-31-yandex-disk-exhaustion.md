# Защита production VM от переполнения диска бэкапами

**Дата:** 2026-08-31  
**Статус:** implementation ready  
**Область:** Yandex production VM, ежедневные PostgreSQL и Supabase Storage backups

## Проблема

31 августа `api.recycleobject.ru` начал отвечать `502`: системный диск production
VM объёмом 39 ГБ заполнился на 100%, PostgreSQL не смог создать временный WAL-файл,
а calculator API завершился после потери соединения с базой. Клиент корректно
показал красную плашку о неподтверждённом сохранении.

Два backup-контура усилили инцидент:

- `backup-ro-site-supabase.sh` удаляет старые локальные поколения только после
  создания, загрузки и обратной проверки нового архива. При нехватке места скрипт
  падает до ротации и оставляет неполный текущий набор файлов.
- `Yandex production backup` сохраняет ежедневную копию активной PostgreSQL на VM
  без локальной ротации, хотя проверенная копия уже находится в versioned Object
  Storage.

## Цели

- Удалять просроченные локальные копии до создания следующего backup.
- Не начинать backup при запасе диска меньше безопасного порога.
- Удалять только неполные файлы текущего запуска, если backup завершается ошибкой.
- Ограничить локальные поколения активной PostgreSQL семью днями, сохранив все
  загруженные поколения в versioned Object Storage.
- Не удалять Docker-контейнеры, volumes, production-данные или облачные backup.

## Решение

1. В site-backup вынести scoped-ротацию в функцию и запускать её до `pg_dump`.
2. Проверять минимум 2 ГиБ свободного места после ротации и до создания файлов.
3. Установить `EXIT`-trap, который при ошибке удаляет только четыре артефакта с
   timestamp текущего запуска и временную директорию обратной проверки.
4. В GitHub workflow production-backup применять тот же порядок на VM:
   scoped-ротация старых `target-yandex-postgres-*`, проверка свободного места,
   запись нового dump во временный файл и атомарное переименование после проверки.
5. Обновить smoke-проверки, чтобы они фиксировали порядок ротации, disk guard и
   узкую область удаления.

## Инварианты

- Облачные backup и их versioning не меняются и не удаляются.
- Последние семь дней локальных копий сохраняются для быстрого восстановления.
- Cutover/preservation bundles не входят в локальную ротацию.
- Backup не удаляет контейнеры, Docker volumes или PostgreSQL data directory.
- Пользовательские API и схема базы не меняются.

## Проверка

- `node tests/ro-site-backup-smoke.js`
- `node tests/yandex-backup-workflow-smoke.js`
- `node tests/version-smoke.js`
- `bash -n ops/infra/scripts/backup-ro-site-supabase.sh`
- Public `https://api.recycleobject.ru/api/health` возвращает `200` и `db.ok=true`.

## Вне области

- Удаление preservation/cutover backup.
- Автоматическая очистка Docker images или volumes.
- Изменение размера диска VM.
- Косметическое скрытие красной плашки при реальной недоступности базы.
