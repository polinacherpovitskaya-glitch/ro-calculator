# Учёт времени: свежие данные и production write-back smoke

## Проблема

После переноса `calc.recycleobject.ru` и Supabase в Yandex ручная запись часов
успешно попадает в `db.recycleobject.ru`, но сразу после сохранения интерфейс
загружает статический bootstrap-снимок. Если снимок ещё не обновлён, свежая
строка исчезает из таблицы и создаётся впечатление, что бот или калькулятор не
записал часы.

Текущий `Yandex write-back smoke` проверяет резервный API Gateway и несколько
служебных таблиц, но не проверяет production-путь часов:

`calc.recycleobject.ru` → `db.recycleobject.ru` → `time_entries`.

## Требуемое поведение

- При доступной Yandex DB `loadTimeEntries()` сначала читает живую таблицу
  `time_entries`.
- Статический bootstrap и локальный кэш остаются fallback при недоступной БД.
- После ручной записи или удаления новый список часов сразу отражает состояние
  Yandex DB и не перезаписывается устаревшим snapshot.
- Почасовой `Yandex write-back smoke` использует Origin
  `https://calc.recycleobject.ru`.
- Smoke создаёт временную запись в `time_entries`, читает её из Yandex DB,
  проверяет поля и удаляет даже при падении последующих проверок.
- Существующая проверка резервного API Gateway и остальных transient-таблиц
  сохраняется.
- При падении smoke продолжает использовать существующие Telegram/GitHub
  incident-уведомления.

## Безопасность

- Тестовая запись имеет уникальный `RO_SMOKE` marker.
- Запись не привязана к реальному сотруднику или заказу.
- Cleanup выполняется в `finally`; успешный smoke отдельно подтверждает, что
  запись больше не существует.
- В артефакты и логи не попадают ключи Supabase.

## Границы

- Парсер Telegram-отчётов и расписание напоминаний не меняются.
- Telegram relay остаётся временным транспортным исключением.
- Общая стратегия bootstrap для заказов, склада и других модулей не меняется.

## Приёмка

- Регрессионный тест доказывает, что живые часы имеют приоритет над устаревшим
  bootstrap.
- При ошибке живой БД часы продолжают открываться из bootstrap/local fallback.
- Write-back smoke проверяет transient `time_entries` с production Origin и
  подтверждённым cleanup.
- Версия приложения повышена до `v421`.
