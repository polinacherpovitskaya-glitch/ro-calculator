# Защита позиций заказа от удаления + быстрый сервер для заказа

## Проблема

В заказе «Лимон» после правки шт/ч пластика пропала фурнитура, потом наоборот — пластик.
Калькулятор «прыгает», связь с базой постоянно отваливается.

Причины (найдены по коду):

1. `POST /api/compat/order-save` удаляет **все** позиции заказа, которых нет в присланном
   списке. Любой неполный список из калькулятора = безвозвратная потеря строк.
2. Неполный список возникает так:
   - `loadOrder()` при ответе сервера дольше 5 с молча открывает заказ из локальной копии
     или статического снимка — они бывают старыми, и автосохранение отправляет их как истину;
   - `Calculator.loadOrder()` рисует пластик, потом `await`-ит загрузку склада для фурнитуры —
     правка в этот момент автосохраняет заказ без фурнитуры;
   - перезагрузка страницы посреди загрузки сохраняет полузагруженный черновик, который потом
     восстанавливается и сохраняется.
   - в fallback-путях `loadOrder()` ещё и вызывает `_rewriteOrderItems` (delete-all + insert) по
     локальным данным.
3. Сервер на каждый select и каждое сохранение читает **всю** таблицу `order_items`
   (с base64-фото) из `compat_rows` и фильтрует в Node, а сохранение ещё и блокирует обе
   таблицы целиком. Запросы дольше 5 с → красная плашка «нет связи» → пункт 2.

## Решение

### A. Сервер удаляет только известные клиенту позиции
- `order-save` принимает `knownItemIds` — id позиций, которые клиент реально держит в форме
  после полной загрузки заказа с сервера (или сохранил сам в этой сессии).
- Строка заказа, которой нет во входящем списке, удаляется **только** если её id есть в
  `knownItemIds`. Остальные сохраняются и возвращаются в `data.items`.
- Нет `knownItemIds` (старая вкладка со старым бандлом, склад, маркетплейсы) → ничего не удаляем.
- `allowEmptyItemsDelete` (сборка из остатков) работает как раньше.
- Тот же принцип в query-builder fallback в `js/supabase.js`.

### B. Клиент не сохраняет неполный/устаревший заказ
- `loadOrder()` возвращает `source: 'remote' | 'bootstrap' | 'local'`; fallback-пути больше не
  делают `_rewriteOrderItems`.
- `Calculator.loadOrder()`: пока заказ грузится — автосохранение и ручное сохранение ждут;
  `knownItemIds` выставляются только в конце полной загрузки с сервера.
- Если заказ открыт не с сервера — форма помечается «открыт из локальной копии», сохранение
  в базу блокируется с понятным сообщением (локальный черновик сохраняется как раньше).
- Черновик в localStorage хранит `known_item_ids` только если снят после полной загрузки.
- `Calculator.loadOrder()` прерывается, если за время `await` форму сбросили или открыли другой
  заказ (`_formToken`, `_loadRequestSeq`). Иначе остаток старого заказа попадал в чистую форму
  без id и автосохранялся новым «Черновиком» — так фурнитура «Лимона» оказалась в
  «Черновик 27.10 13:46».

### C. Сервер выбирает строки заказа в SQL
- `readCompatRows` принимает SQL-предфильтр: `source_id = …` для eq по `id`, и
  `data @> {"col": N} OR data @> {"col": "N"}` (GIN `compat_rows_data_gin_idx`) для eq по
  целочисленному значению. JS-фильтр остаётся как окончательная проверка.
- `order-save` читает только строку заказа, строки этого заказа и строки с входящими id,
  вместо обеих таблиц целиком.

## Не входит
- Восстановление позиций «Лимона» из бэкапа — отдельный шаг руками (нужен доступ к бэкапу).
- UX калькулятора (прыжки вёрстки при загрузке) — ops/web backlog.
- Миграция `order_items` в нормализованные таблицы.

## Риски
- Удаление позиции из старой открытой вкладки не применится до обновления страницы — это
  сознательный размен на отсутствие потерь.
