# Один production-калькулятор и быстрый deploy

## Контекст

Сейчас один и тот же production-калькулятор полностью публикуется в два бакета:
`calc.recycleobject.ru` и `calc2.recycleobject.ru`. Файлы в каждый бакет загружаются
последовательно, поэтому одна доставка занимает примерно 18 минут. Дополнительно
полный deploy запускается каждые 30 минут независимо от наличия изменений. Это
создаёт две точки входа, риск расхождения версий и ощущение бесконечного deploy.

## Цель

- Оставить `https://calc.recycleobject.ru/` единственным production-приложением.
- Не ломать старые закладки на `calc2`: этот домен должен только перенаправлять на
  `calc`, а не обслуживать вторую копию приложения.
- Сократить время публикации за счёт одной сборки, одной полной загрузки и
  параллельной отправки файлов.
- Запускать deploy только после успешной проверки `main` или вручную, без cron.
- Запускать production-smoke после завершения фактической публикации новой версии.

## Решение

### Единственная production-копия

Полный статический bundle публикуется только в бакет `calc.recycleobject.ru`.
`calc2.recycleobject.ru` получает минимальные `index.html` и `404.html`, которые
перенаправляют пользователя на `https://calc.recycleobject.ru/`, сохраняя query и
hash. Старые файлы в бакете не удаляются: это исключает риск потери данных и не
мешает редиректу с пользовательских URL.

### Быстрый и безопасный deploy

После единственной сборки файлы загружаются в таком порядке:

1. ассеты и данные, кроме HTML и `js/version.json`, — параллельно;
2. HTML — после ассетов;
3. `js/version.json` — последним как маркер полностью опубликованной версии;
4. после проверки версии — два маленьких redirect-файла для `calc2`.

Параллелизм ограничивается, чтобы ускорить доставку и не перегружать Object
Storage. Workflow сохраняет concurrency без отмены начавшегося deploy: новая
публикация ждёт завершения предыдущей и не оставляет бакет в промежуточном
состоянии.

### Проверки

- Основной live smoke и platform/API smoke проверяют `calc.recycleobject.ru`.
- Автоматические smokes запускаются после workflow фактической статической
  публикации, а не до неё.
- Отдельный smoke фиксирует инварианты pipeline: один полный бакет, отсутствие
  cron deploy, параллельная загрузка, публикация version-файла последним и наличие
  безопасного редиректа `calc2`.
- Почасовой write-back smoke остаётся: это мониторинг сохранения данных, а не
  повторный deploy.

## Границы

- API Gateway, Cloud Function и Supabase/PostgreSQL не переносятся и не удаляются.
- Данные и старые объекты бакета `calc2` не удаляются.
- Текущий Vercel relay остаётся частью существующего release gate; эта задача
  оптимизирует фактическую публикацию калькулятора в Object Storage.
- Исторические тесты совместимости старого proxy-runtime не удаляются.

## Критерии готовности

- `calc.recycleobject.ru` показывает новую версию и проходит live, platform/API и
  write-back проверки.
- `calc2.recycleobject.ru` перенаправляет на `calc.recycleobject.ru` и больше не
  загружает приложение.
- Workflow полного статического deploy не содержит schedule и не загружает полный
  bundle во второй бакет.
- Файлы основного bundle загружаются параллельно с безопасным порядком публикации.
- Версия приложения поднята во всех четырёх обязательных местах; локальные smoke
  и GitHub Actions проходят.
- Фактическое время нового deploy измерено по GitHub Actions и зафиксировано в
  результате задачи.
