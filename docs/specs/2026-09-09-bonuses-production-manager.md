# Бонусы: страница владельца и схема начальника производства

**Дата:** 2026-09-09
**Статус:** design approved, план: `docs/plans/2026-09-15-bonuses-production-manager.md`

## Проблема

Начальник производства (Лёша) получает оклад и не понимает, какая у него
мотивация. У коммерческого отдела схема прозрачная: общий план, личный процент
от оборота, понятные пороги. У производства привязать бонус к обороту нельзя
(он не продаёт), а к чистой прибыли нельзя тем более: она зависит от косвенных,
аренды и налогов, а в Q1 по модели отрицательная, потому что Q1 кормится из
Q3/Q4. Схема «нет прибыли, нет бонуса» разрушает доверие.

Полоса загрузки производства показывает часы табеля против сезонного плана и
единой цифрой «недобор». Она не отвечает на вопрос «что из этого зона
производства», и платить за часы табеля нельзя: это плата за занятость, а не за
результат.

Владелец хочет вести бонусы внутри системы, на странице, которую видит только
она, и чтобы факт считался из данных, а не руками.

## Цель

Страница «Бонусы» в calc, доступная только владельцу, где по каждому кварталу
видно план (мин/цель/макс), факт, прогноз и сумму бонуса, а закрытые кварталы
хранятся в журнале. Первая схема: начальник производства, привязка к выпуску
цеха в нормо-часах.

Этот документ описывает ядро (схемы, цели, результаты, страница) и схему
производства. Схема коммерческого отдела описана отдельно в
`docs/specs/2026-09-09-bonuses-commercial-team.md` и строится на этом ядре.

## Где живёт

Живые данные calc лежат в `compat_rows` на `api.recycleobject.ru`; ops/web
пока staging. Поэтому:

- расчёт и хранение бонусов делаем в `ops/api` (новый модуль
  `ops/api/src/bonuses/`, маршруты `/api/bonuses/*`, миграция
  `ops/db/migrations/019_bonuses.sql`);
- страницу делаем в calc (`js/bonuses.js`, страница `bonuses`);
- при переезде на ops/web переносится только страница, API остаётся.

Расчёт читает legacy-таблицы из `compat_rows`: `orders`, `time_entries`,
`employees`, `settings`. Для этого `readRows` из `routes/compat.js` выносится в
общий модуль и переиспользуется, без второго парсера строк.

## Доступ

- Все маршруты `/api/bonuses/*` под `requireAuth, requireRole('admin')`.
- Страница `bonuses` показывается только когда
  `currentUser.role === 'admin'` и `employee_id` пуст (условие владельца в
  `App.canAccess`). Страницы нет в `DEFAULT_PAGES`, её нельзя выдать сотруднику
  через права страниц в настройках.
- Первый шаг плана: проверить на VM, что роль `admin` в `auth_users` есть
  только у владельца. Если есть у кого-то ещё, роль у них меняется на `user` до
  выкладки страницы.

## Модель данных (миграция 019, доступ только из API)

`bonus_schemes`

- `id`, `employee_id` (legacy id сотрудника из `compat_rows.employees`),
  `kind` (`production` | `commercial`), `period_type` (`quarter`),
  `target_amount` (сумма бонуса при выполнении целей, ₽),
  `metrics_json` (список `{key, weight, direction}`),
  `ladder_json` (`{below_min: 0, min: 0.5, target: 1, max: 1.5}`),
  `is_active`, `created_at`, `updated_at`.
- У сотрудника не больше одной активной схемы.

`bonus_period_targets`

- `id`, `scheme_id`, `period` (`2026-Q4`), `metric_key`,
  `min_value`, `target_value`, `max_value`, `note`, `updated_at`.
- Уникально по `(scheme_id, period, metric_key)`.
- Значения хранятся явно. Изменение сезонного плана после сохранения целей не
  двигает планку молча: интерфейс показывает «сезонный план изменился, цель
  отличается» и предлагает пересохранить.

`bonus_stock_approvals`

- `period`, `order_id`, `approved_by`, `approved_at`. Уникально по
  `(period, order_id)`.
- Складской заказ (`production_purpose = stock_sample`) идёт в зачёт выпуска
  только при наличии записи.

`bonus_period_results`

- `id`, `scheme_id`, `period`, `status` (`open` | `closed` | `paid`),
  `computed_json` (полный снимок расчёта на момент закрытия: факты, достижения,
  выплата по показателям, предупреждения, список заказов),
  `amount_computed`, `amount_final`, `adjustments_json`
  (список `{at, by, from, to, comment}`), `closed_at`, `closed_by`,
  `paid_at`.
- Уникально по `(scheme_id, period)`.
- Пока результат `open`, страница считает всё заново при каждом запросе.
  После `closed` показывается снимок, факт больше не пересчитывается.

## Дата завершения заказа

У legacy-заказа статус `completed` есть, а даты перехода в него нет. Для бонуса
дата нужна, поэтому:

- API в пути записи заказа (`executeAtomicOrderSave` и мутация статуса в
  `routes/compat.js`) при первом переходе в `completed` записывает
  `completed_at = now()` в строку заказа, если поле пустое. Интерфейс calc не
  меняется.
- Для заказов, завершённых раньше, дата берётся так: последняя дата записи
  табеля по заказу, иначе `updated_at`. Такие заказы помечаются как «дата
  оценочная» в деталях карточки и в предупреждениях.

## Показатели схемы производства

Период: календарный квартал. Заказ «завершён в периоде», если его статус
`completed` и дата завершения попадает в период.

| key | Что считаем | Направление | Вес |
|---|---|---|---|
| `output_hours` | сумма `total_hours_plan` коммерческих заказов, завершённых в периоде, плюс `total_hours_plan` складских заказов, завершённых в периоде и утверждённых для периода | больше лучше | 0.50 |
| `productivity` | `output_hours` / сумма часов табеля по тем же заказам за всё время | больше лучше | 0.25 |
| `on_time_share` | доля завершённых коммерческих заказов с дедлайном, у которых дата завершения не позже `deadline` | больше лучше | 0.15 |
| `rework_share` | часы табеля периода по заказам `rework` / (эти часы + часы табеля периода по коммерческим заказам) | меньше лучше | 0.10 |

Правила:

- Коммерческий заказ: `production_purpose` не `rework` и не `stock_sample`
  (пустой, `commercial`, `leftover_assembly`), статус не `cancelled`, нет
  `deleted_at`. Определение совпадает с полосой загрузки.
- Заказы без `total_hours_plan` (0 или пусто) в выпуск не входят и попадают в
  предупреждение со списком.
- Если часов табеля по завершённым заказам нет, `productivity` не считается,
  его доля бонуса равна нулю, показывается предупреждение «табель не заполнен».
  Пустой табель не подменяется догадкой.
- Заказы без `deadline` из `on_time_share` исключаются и попадают в
  предупреждение с количеством.
- Записи табеля без `order_id` за период выводятся отдельным предупреждением с
  суммой часов, как в полосе загрузки. Никуда не приписываются.

## Достижение и сумма

Для показателя «больше лучше» с порогами `min ≤ target ≤ max`:

- факт ниже `min`: достижение 0;
- от `min` до `target`: линейно от 0,5 до 1,0;
- от `target` до `max`: линейно от 1,0 до 1,5;
- выше `max`: 1,5.

Для «меньше лучше» пороги задаются как `min` (худший допустимый), `target`,
`max` (лучший), и шкала зеркальная. Коэффициенты 0,5 / 1,0 / 1,5 берутся из
`ladder_json` схемы.

Бонус периода = `target_amount × Σ (weight × достижение)`. Все веса схемы в
сумме дают 1.

Проверочный пример (для теста): `target_amount = 100 000`, выпуск 1 700 при
порогах 1 360 / 1 600 / 1 840 даёт достижение 1,208; производительность 1,05
при 0,9 / 1,0 / 1,15 даёт 1,167; в срок 90% при 70 / 85 / 95 даёт 1,25;
переделки 4% при 8 / 5 / 2 даёт 1,167. Сумма:
`100 000 × (0,5×1,208 + 0,25×1,167 + 0,15×1,25 + 0,10×1,167) = 100 000 × 1,200 = 120 000 ₽`
(округление до рубля).

## Подсказка целей из сезонного плана

Для нового периода API отдаёт предложение целей, владелец его правит и
сохраняет:

- `output_hours.target` = часы квартала из `seasonal_load_plan_json` (ключ
  `Qn`), иначе формула `workers_count × hours_per_worker × work_load_ratio × 3`,
  как в `quarterTargetHours`; `min` = 85% от цели, `max` = 115%;
- `productivity`: 0,9 / 1,0 / 1,15;
- `on_time_share`: 0,70 / 0,85 / 0,95;
- `rework_share`: 0,08 / 0,05 / 0,02.

## Прогноз

Только для открытого периода и только для `output_hours`: факт делится на долю
прошедших рабочих дней квартала. Рабочие дни: понедельник–пятница минус даты из
`production_holidays`. Остальные показатели показывают текущее значение.
Прогноз подписан «если темп сохранится» и в сумму бонуса не входит.

## Годовой добор

Считается только по `output_hours`. За год суммируются факты и пороги четырёх
кварталов, достижение считается по той же шкале. Годовая доля выпуска =
`Σ target_amount × weight_output × годовое достижение`. Добор =
`max(0, годовая доля − Σ выплаченных квартальных долей выпуска)`.
Показывается строкой «Год» на странице, фиксируется кнопкой «Закрыть год»,
попадает в журнал как результат с периодом `2026-Y`.

## API

- `GET /api/bonuses/schemes` и `PUT /api/bonuses/schemes/:employeeId`.
- `GET /api/bonuses/periods/:period` — расчёт всех активных схем за период:
  показатели, достижения, суммы, прогноз, предупреждения, список заказов и
  складских заказов с признаком утверждения. Для закрытых периодов отдаёт
  снимок.
- `GET /api/bonuses/periods/:period/suggest/:schemeId` — предложение целей.
- `PUT /api/bonuses/periods/:period/targets/:schemeId` — сохранить цели.
- `POST /api/bonuses/periods/:period/stock-approvals` — `{order_id, approved}`.
- `POST /api/bonuses/periods/:period/close/:schemeId` — снимок и `closed`.
- `POST /api/bonuses/periods/:period/adjust/:schemeId` — `{amount, comment}`,
  комментарий обязателен, старое значение остаётся в `adjustments_json`.
- `POST /api/bonuses/periods/:period/paid/:schemeId`.
- `GET /api/bonuses/years/:year` — четыре квартала и годовой добор.
- `POST /api/bonuses/years/:year/close/:schemeId`.

Расчёт живёт в чистых функциях `ops/api/src/bonuses/calc.js` (вход: строки
заказов, табеля, целей, настроек и дата; выход: результат). Маршруты только
читают данные и вызывают расчёт.

## Страница

Пункт «Бонусы» в боковом меню, виден только владельцу. Крупный шрифт, без
тесных таблиц.

Сверху выбор периода: кварталы текущего и прошлого года, отдельная строка
«Год». Под ним карточки сотрудников с активной схемой.

Карточка сотрудника:

- имя, тип схемы, сумма на цели, статус периода;
- по каждому показателю строка: название, полоса с рисками мин / цель / макс,
  факт крупно, прогноз бледнее, достижение в процентах, выплата в рублях;
- итоговая строка: сумма бонуса, при корректировке рядом исходная сумма;
- блок предупреждений: часы без заказа, заказы без дедлайна, заказы без
  нормо-часов, оценочные даты, пустой табель.

Детали открываются под карточкой, без прокрутки вниз: список заказов периода
(название, нормо-часы, часы табеля, дедлайн, дата завершения, в срок или нет),
складские заказы с переключателем «в зачёт», кнопки «Цели квартала»,
«Закрыть квартал», «Корректировка», «Выплачено».

Диалог «Цели квартала»: три поля на показатель, кнопка «Взять из сезонного
плана», пометка, если сезонный план изменился после сохранения.

Внизу журнал: закрытые периоды с суммами расчёта и итога, статусом и
комментариями корректировок.

## Что меняем в calc

- новый файл `js/bonuses.js` и тег `<script>` в `index.html` (согласовано
  этой спекой);
- пункт меню и маршрут страницы `bonuses` в `js/app.js`, исключение страницы
  из прав сотрудников в `js/settings.js`;
- четыре якоря версии и `?v=` у изменённых скриптов по правилу репо.

Формулы полосы загрузки, цен, маржи и payroll не трогаем.

## Границы

- Схема коммерческого отдела: отдельная спека и отдельный PR.
- Разбивка «недобора» в полосе загрузки на «не продано» и «не сделано»:
  отдельная маленькая спека после первых двух.
- Сотрудник свою карточку не видит; владелец показывает её сама.
- Уведомления в Telegram, экспорт, интеграция с payroll: вне scope.
- Не меняем нормы заказов, статусы и дедлайны автоматически.
- Не переносим сезонный план в нормализованные таблицы ops.

## Тесты

`ops/api/test/bonuses.test.js`:

- шкала достижения в обе стороны, включая границы и превышение `max`;
- проверочный пример выше даёт 120 000 ₽;
- складской заказ входит в выпуск только после утверждения;
- пустой табель обнуляет долю производительности и даёт предупреждение;
- заказ без дедлайна не влияет на долю в срок;
- `completed_at` проставляется при первом переходе в `completed` и не
  перезаписывается;
- закрытый период отдаёт снимок, а не пересчёт;
- годовой добор по четырём кварталам;
- пользователь с ролью `user` получает 403 на всех маршрутах.

calc: `tests/bonuses-smoke.js` рендерит страницу на фиктивном ответе API,
проверяет полосы, предупреждения, раскрытие деталей под карточкой и что для
не-владельца пункт меню и страница отсутствуют. `tests/version-smoke.js`
проходит.

## Критерии приёмки

- Владелец видит страницу «Бонусы», обычный сотрудник её не видит и получает
  403 от API.
- Для Q3 2026 страница показывает выпуск, производительность, срок и
  переделки Лёши из живых данных с предупреждениями о неразмеченных часах и
  оценочных датах.
- Цели квартала подтягиваются из сезонного плана одной кнопкой и хранятся
  явно.
- Закрытие квартала фиксирует снимок, корректировка требует комментария и
  сохраняет историю.
- Строка «Год» показывает накопленный выпуск и добор.
