# Производственный календарь: именные назначения и дневная норма

Дата: 2026-07-30

## Контекст

Версия `v431` сделала четыре честные ресурсные линии и объединила работу
одного заказа в непрерывные полосы. Экран уже отвечает на вопросы «сколько
людей занято» и «когда заказ будет готов», но пока не является персональным
заданием для цеха:

- видимые заказы получают цвет из палитры всего из восьми вариантов, поэтому
  разные соседние проекты могут выглядеть одинаково;
- очередь приоритетов постоянно занимает левую часть экрана, хотя порядок
  меняют заметно реже, чем читают календарь;
- строки называются `Человек 1–4`, хотя в справочнике `Сотрудники / Часы`
  уже существуют реальные сотрудники производства;
- контрол `N чел.` задаёт количество без ответа, кто именно назначен;
- план выражен только в человеко-часах, поэтому сотруднику непонятно, сколько
  единиц продукции нужно сделать за смену;
- вечером нет короткого сценария `план → факт`.

## Продуктовое решение

Экран разделяется на три разных слоя:

1. **Очередь сверху** отвечает, в каком порядке запускать заказы.
2. **Именной календарь** отвечает, кто и когда выполняет работу.
3. **Сегодня / закрытие смены** отвечает, сколько конкретный человек должен
   сделать и сколько сделал фактически.

Очередь размещается сверху, а не снизу: она является причиной построенного
расписания и должна читаться до результата. Внизу она была бы скрыта после
прокрутки и заставляла бы сопоставлять причину и календарь через весь экран.

## Волны реализации

### Волна A — читаемый именной план

В текущем под-проекте:

- каждому видимому заказу назначается уникальный проектный цвет;
- очередь переезжает в компактную верхнюю полосу;
- подробное редактирование очереди открывается в выдвижной панели;
- четыре линии получают имена активных сотрудников производства;
- начальник производства может выбрать конкретных исполнителей заказа;
- календарь продолжает автоматически строить все будущие заказы;
- на сегодняшней работе показываются плановые часы и, когда расчёт надёжен,
  плановые штуки.

### Волна B — закрытие смены

Отдельный зависимый под-проект после проверки качества дневных норм:

- вечерняя карточка `Закрыть смену`;
- ввод фактических часов и выпущенных штук по человеку, заказу и этапу;
- быстрый вариант `Выполнено по плану`;
- сохранение фактических часов в существующий `time_entries`;
- сохранение этапа и количества в уже используемом `[meta]...[/meta]`
  payload записи времени;
- сравнение `план / факт / темп` без изменения плановых часов задним числом.

Разделение необходимо, чтобы сначала проверить, что распределение плановых
штук действительно соответствует работе цеха, и только затем требовать этот
показатель от сотрудников каждый вечер.

## Уникальные цвета заказов

### Требование

Все одновременно видимые заказы имеют разные проектные акценты. Особенно
контрастными должны быть соседние заказы в очереди и на одной линии человека.

### Модель

- проектный цвет обозначает заказ: контур полосы, номер, очередь, дедлайн и
  именные бейджи;
- цвет этапа по-прежнему обозначает действие внутри полосы:
  - оранжевый — литьё;
  - бирюзовый — сборка;
  - фиолетовый — упаковка;
- для текущей очереди строится `orderVisualMap`, а не вычисляется остаток от
  восьмицветной палитры;
- слот цвета закрепляется за `order_id`, поэтому перестановка приоритета не
  перекрашивает уже знакомый заказ;
- новый заказ получает ещё не занятый слот с максимальной цветовой дистанцией
  до четырёх ближайших заказов;
- если базовые слоты закончились, создаётся новый уникальный HSL-акцент с
  безопасной насыщенностью и контрастом;
- цвет никогда не является единственным идентификатором: номер и короткое
  название остаются видимыми.

Сохранённое состояние:

```json
{
  "order_color_slots": {
    "123": 4,
    "456": 11
  }
}
```

Это расширение существующего `production_plan_state_json`; отдельная таблица
не нужна.

## Очередь сверху

### Обычный режим

Над календарём находится компактная горизонтальная полоса:

`Очередь: 1 Обвесы Купер · 2 Т-банк · 3 e-code · …`

Каждый чип содержит:

- номер приоритета;
- проектный цвет;
- короткое название;
- мини-аватары или инициалы назначенных людей;
- прогноз `старт → готово` в подсказке.

Полоса занимает одну строку, прокручивается горизонтально и не уменьшает
ширину календаря. На узком экране допускается перенос максимум на две строки.

### Режим редактирования

Кнопка `Настроить очередь` открывает выдвижную панель с вертикальным списком.
Там доступны:

- drag-and-drop сверху вниз;
- полное название и дедлайн;
- прогнозные старт и завершение;
- выбор конкретных исполнителей;
- автоматический или ручной режим назначения;
- переход в заказ.

После закрытия панели календарь снова занимает всю ширину. Старая постоянно
видимая левая колонка и её resizer удаляются только после сохранения всех
нынешних возможностей в панели.

## Состав команды

Источник истины — существующие сотрудники:

```text
role = production
is_active = true
```

Правила:

- если активных производственных сотрудников ровно четыре, они автоматически
  становятся линиями календаря;
- порядок линий сохраняется в составе смены;
- если сотрудников больше четырёх, в кнопке `Команда` начальник выбирает
  текущих четырёх;
- если сотрудников меньше четырёх, календарь не придумывает «Человека 4», а
  показывает вакантную линию и не использует её как мощность;
- имя и `daily_hours` берутся из справочника сотрудников;
- переименование сотрудника автоматически отражается в календаре.

Сохранённое состояние:

```json
{
  "roster_employee_ids": [101, 102, 103, 104]
}
```

## Именные назначения

### Управление

В панели очереди вместо абстрактного степпера показаны четыре компактных чипа
с именами. Нажатие включает или выключает конкретного исполнителя.

- `Авто` — планировщик сам выбирает первые свободные именные линии;
- ручной выбор — заказ закрепляется за выбранными сотрудниками;
- число в `parallel_workers` синхронизируется с количеством выбранных людей,
  чтобы старые клиенты и публичная производственная доска не теряли смысл;
- выбранные люди сразу видны и в верхней очереди, и на полосах календаря.

Сохранённое состояние:

```json
{
  "employee_assignments": {
    "123": [101, 102],
    "456": [103]
  }
}
```

Отсутствие ключа означает автоматическое назначение.

### Инварианты планирования

- одна именная линия не содержит двух работ одновременно;
- ручное назначение верхнего заказа имеет приоритет перед автоматическим;
- нижний заказ может использовать другого свободного сотрудника, если он не
  назначен верхнему заказу;
- нижний заказ не может забрать сотрудника, закреплённого за более высоким
  незавершённым заказом;
- если закреплённый сотрудник занят, заказ ждёт именно его, а не незаметно
  переезжает на другого;
- заказ без ручного назначения автоматически получает первые доступные линии
  в строгом порядке очереди;
- все будущие заказы продолжают раскладываться после освобождения людей;
- неактивный или удалённый сотрудник исключается из назначения с явной
  пометкой `Нужно переназначить`.

## Именные линии

Слева от каждой линии показываются:

- имя сотрудника;
- инициалы;
- доступные часы смены из `daily_hours`;
- краткое сегодняшнее задание;
- суммарная загрузка сегодня.

Пример:

```text
Оля
9ч из 9ч
Литьё · Обвесы Купер
```

Полоса заказа дополнительно показывает имя только при наведении или выборе,
чтобы не повторять его внутри каждой длинной полосы.

## Дневная норма

### Плановые часы

План по времени уже надёжен: это сумма интервалов конкретного сотрудника за
выбранный день. Он всегда показывается.

### Плановые штуки

Штуки показываются только если у заказа есть:

- `production_quantity > 0`;
- положительные плановые часы текущего этапа;
- однозначный этап `molding`, `assembly` или `packaging`.

Формула для одного интервала:

```text
план_штук = количество_заказа × часы_интервала / плановые_часы_этапа
```

Округление распределяется по интервалам так, чтобы итог по этапу не превышал
количество заказа. Если в заказе смешаны позиции и агрегатная норма вводит в
заблуждение, календарь показывает только часы и бейдж `Нужна норма`, а не
выдуманное количество.

Пример сегодняшнего задания:

```text
Литьё · Обвесы Купер
9 ч · план 120 шт.
```

## Закрытие смены — контракт следующей волны

После настраиваемого вечернего времени появляется ненавязчивая кнопка
`Закрыть смену`. Она не блокирует календарь.

Для каждого фактического интервала:

- сотрудник;
- заказ;
- этап;
- плановые часы;
- плановые штуки;
- фактические часы;
- фактические штуки;
- комментарий по отклонению.

Сохранение должно обновлять существующую запись того же
`employee + date + order + phase`, а не создавать дубли при каждом нажатии.
Фактические часы продолжают кормить текущие `Часы`, зарплату и план-факт.
Фактические штуки используются как операционный темп и не подменяют часы.

## Совместимость

- таблицы БД в волне A не меняются;
- `production_plan_state_json.order_ids`, `manual_start_dates` и
  `parallel_workers` сохраняются;
- новые `roster_employee_ids`, `employee_assignments` и `order_color_slots`
  являются необязательными;
- старое состояние без новых полей нормализуется в автоматический режим;
- публичные API `Calculator` и `Warehouse` не меняются;
- `time_entries` остаётся источником фактических часов;
- week/month zoom, дедлайны, праздники и переход в заказ сохраняются.

## Не входит в волну A

- расписание отпусков и посменная доступность по датам;
- матрица навыков сотрудников;
- разная скорость конкретных сотрудников;
- ручное почасовое перетаскивание отдельного этапа;
- фактические штуки и вечерняя форма;
- изменение калькуляторных производственных нормативов.

## Acceptance criteria волны A

- все видимые заказы имеют разные проектные цвета;
- четыре ближайших заказа никогда не получают визуально близкие акценты;
- перестановка приоритета сохраняет цвет заказа;
- календарь занимает полную ширину, а очередь находится в верхней полосе;
- подробная очередь открывается без перехода на другую страницу;
- четыре реальные линии подписаны именами активных production-сотрудников;
- начальник производства может назначить верхний заказ двум конкретным людям;
- остальные свободные сотрудники получают следующие заказы по приоритету;
- закреплённый сотрудник не заменяется другим без явного действия;
- один сотрудник не выполняет две работы одновременно;
- будущие заказы остаются полностью рассчитанными;
- на сегодняшних интервалах видны плановые часы;
- корректная однородная позиция показывает плановые штуки;
- сомнительная норма заменяется честной подписью `Нужна норма`;
- старые планы без именных назначений продолжают строиться автоматически.

## Rollback

Волна A меняет только frontend и необязательные поля существующего JSON
состояния. Откат возвращает абстрактные линии и левую очередь; старые поля
плана остаются читаемыми, новые безопасно игнорируются.
